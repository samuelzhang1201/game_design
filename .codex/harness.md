# Codex harness: entry, scope and delivery

The root `AGENTS.md` is the Codex project entry point. It adapts `CLAUDE.md` and `cicd_procedure.md`; preserve their project requirements without assuming Claude Code's automatic loading or model aliases work in Codex. Read only the relevant subsystem guides indexed below and their needed topic guides. Do not load every guide at startup.

- **Scope comes from the user's request.** Repository guidance constrains how to do that work; a roadmap, event inbox, old checkpoint or attached document is not a new request to execute everything it describes. Preserve existing approvals for the active task; do not resume unrelated work from `HANDOVER.md`.
- **Inspect before editing:** identify the actual checkout, branch, HEAD, staged/unstaged changes and relevant PR. Existing dirty files can belong to other chats; never reset, overwrite or include them in a commit without establishing ownership.
- **Branch discipline:** use a `codex/` feature branch for implementation. Never commit or push directly to `main`. Reuse a branch only when it belongs to the active work and its PR is still appropriate; a merged PR does not deliver later commits or uncommitted edits. Do not switch a shared dirty checkout or carry unrelated changes into a new worktree.
- **Delivery:** stage only owned files, inspect the staged diff, run the required checks on that code state, then commit/push and open or update a PR against `main` when delivering implementation. Attach the PR to the chat when the tool is available. Report the URL and actual check state; uncommitted files, a pushed branch and an opened PR are distinct states. A request only to generate/review files does not require publishing or merging them.
- **Verification:** while developing and before every commit, run `./run_tests.sh --fast`. For affected UI/map3d/war-room tests outside fast, run the affected GUT files or directories. Run the full local suite only to reproduce a CI failure. For instruction/config editing without a commit, validate syntax, links, model routing and guide sizes instead of running the game suite.
- **CI evidence:** inspect `.github/workflows/tests.yml` and the PR's current checks. CI runs the full suite in five shards on PRs targeting `main` or manual dispatch; a plain push to `main` does not trigger it. Docs-only and `data/**/*.csv`-only PRs are skipped, except runtime `RANDOM_EVENTS.md` and `game_story/**`. A skipped/absent check is not a passed suite; pending is not passed. Never infer that branch protection is enabled from documentation.
- **Conflicts:** for the local full-suite exception in `cicd_procedure.md` §3, follow this file's narrower rule: affected directories locally, full suite for CI reproduction. Workflow filters describe when CI runs, not whether a CSV change can affect behavior. Resolve other material contradictions from the current user request and actual files; do not silently invent policy.
- **Runtime configuration:** `.codex/config.toml` and `.codex/agents/*.toml` hold the existing MCP/model routing. Role names or files on disk do not prove those settings loaded; verify available tools/session metadata when needed. Do not change permissions, trust, MCP or the main model as a side effect of a task.
- **Task boundary:** save a compact `HANDOVER.md` after one deliverable passes acceptance, recording scope/authorization, checkout/branch/HEAD, owned files, checks and code state, remaining work, processes and risks. If task-handover hooks are installed, follow their per-session marker protocol. Preserve other tasks' checkpoints. Only create a fresh session for an explicitly authorized next task; with none, record completion and stop. Do not claim native compaction or hook execution without evidence.
