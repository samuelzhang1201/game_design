# Crown and Council

Text-first, LLM-narrated grand strategy game: rule a kingdom for ~60 years through a council of ministers with real personalities, ideologies, and grudges. **Greenfield** — no code exists yet; this directory currently holds design docs and data.

## Key documents

- `PRD.md` — scope of the first playable build. Build order lives here; follow it.
- `COUNCIL_SYSTEM.md` — the council design doc; source of truth for mechanics and formulas.
- `MANOR_SYSTEM.md` — the manor system (owner 2026-09-13): every land cell of the pack is a **manor** with a proper name (`political/manors.csv`, forged by `NameForge` / `ManorNames` from the export's name banks; `manor_name_overrides.csv` is hand-maintained) held by a **house** (a family name; the crown is the player character's live family; an unmoved manor belongs to its province's house, so `GameState.manor_owner` holds only what moved and `MapManors.set_owner` needs a reason — `manor_log`). People are never stored: a manor's share of its province's ledger population is area × land value, so manors always sum to their province. Buildings (`data/manor_buildings.csv`), rent (paid into the treasury each tick as `manor_rents`), defence, value and the holding house's asking price (marked up by its councillor's opinion) are `MapManors`, every number `balance.csv` `manor_*`. Orders `MANOR_BUY` / `MANOR_SELL` / `MANOR_BUILD` / `MANOR_SEIZE` (a skeleton gated by `manor_seize_enabled`) resolve a manor by code, label or id (`MapManors.find`) and run from the manor card's buttons through `Game.try_execute`. `world_cell_index.png` (importer / `tools/bake_manors.gd`) is how a click finds its manor — only in the ECONOMY and MANORS layers; on the political map land still means province. The **MANORS** tab colours manors by house (`MapPalette.house_color`), puts the **Manor Master** table in the left column, and is the ONLY view that draws each manor's **farmsteads and chief-good marks** (`data/manor_decor.csv`, `MapObjects.manor_decor`: one farmstead per `per_people` of the manor's people up to `max_clump`, plus the working focus's marks where art exists, placed by cell-id hashes, in palette `manor_mark` ink, one `MarkMesh` per zoom tier) — owner 2026-09-13: the default map stays as it was. **The player is the king of the realm and the lord of ONE province** (owner 2026-09-13): a province is controlled by the house holding the most of its manors (`MapManors.controller_of`, ties to the province's own house), the crown starts controlling the capital's province alone (`house_bindings.csv`), and everything that reads as the crown's economy — the seeded treasury, the dashboard's people and provinces, the ECONOMY column, `WorldLedger.belongs_to_player`, the order prompt's "Your provinces" — is `MapManors.controlled_provinces`; the host stays the realm's; BUILD and FOCUS need a controlled province, BUY and SEIZE any province of the realm. Every manor works one **chief good** (`data/manor_focus.csv`, allowed by biome and coast; the default is the first allowed; `GameState.manor_focus` holds only chosen ones with the tick, ramping in over `transition_ticks`): yield is people × land value × `yield_per_1000`, it adds `rent_bonus` to the rent, counts in the value, and joins the ECONOMY column through `MapEconomy.output_of_provinces(repo, provinces, state)`; `MANOR_FOCUS` runs from the card's `WORK` buttons like the other manor orders — no model call. **Time runs in days** (owner 2026-09-13): `GameState.day` (1..15) under the tick, the top bar's clock (`||` `>` `2x` `4x`, `time_day_seconds`, `time_speed_*`) driven only by `GameRoot._process` on the court through `Game.advance_day` — works step each day, the fifteenth day's end is the tick, an event stops the clock and opens the council, End Turn stops it; no wall-clock below `Game`. **Building takes time and room**: `build_days` per building, works in `GameState.manor_works`, `manor_slots_base` (+`manor_slots_burg_bonus`) slots per manor, `MANOR_DEMOLISH` refunds `manor_demolish_refund`; finished buildings add `*_per_tick` (gold, grain, church, contentment, unrest) as ledger lines after the rents and `produce_good/units` to the ECONOMY column; the card's slot row (`MapDetailPanel._fill_slots`, icons `bld_*` in `resource_icons.csv`) carries a cross per building.
- `RANDOM_EVENTS.md` — random-events system: triggering rules + the event pool. The "Your event seeds" section at the top is the owner's inbox for raw ideas — when new seeds appear there, expand each into a fully spec'd event (trigger, weight, choices with signatures, chain) in the pool below it. **This file is loaded at runtime**, not just design reference: `StorySource` parses each `### EV-NN` entry's `**Scene:**` field and the game displays that prose verbatim. Its formatting is therefore a contract — keep the heading and `**Scene:**` labels intact, and a test asserts all 20 ids still resolve. **No event is ever model-written:** event stories are fixed authored prose, `Voicer.voice_event` has no path to the API, and no event prompt exists. If an event needs different words, write them here.
- `council_seats.csv`, `character_traits.csv`, `faction_escalation.csv`, `policy_actions_court_additions.csv`, `action_signatures.csv`, `events.csv`, `event_choices.csv`, `world_rules.csv`, `claim_types.csv`, `facts.csv`, `world_schema.csv`, `metric_polarity.csv`, `order_costs.csv`, `political_palette.csv`, `kingdoms.csv`, `provinces.csv`, `burgs.csv` — game data, loaded at runtime. **Design values live in these CSVs, never hardcoded in scripts.** Add columns/rows rather than embedding constants. Exception: the map pack tables under `data/maps/<id>/` — `map_info.csv`, `realm_bindings.csv`, and `house_bindings.csv` (both bindings hand-maintained, never written by the importer: realms bind authored slots to kingdoms, houses bind the court's families to provinces of the player's realm; unbound provinces are held by a house named after their seat) at the root and, by domain, `geography/` (`biomes`, `rivers`, `markers`, `routes`), `political/` (`kingdoms`, `provinces`, `burgs`, `borders`, `province_borders`, `diplomacy`, `campaigns`), `economy/` (`kingdoms`, `provinces`, `burgs`, `goods`, `markets`, `market_goods`, `production`), `military/` (`kingdoms`, `regiments`, `unit_types`), `society/` (`cultures`, `religions`, `zones`); `data/` carries a `.gdignore` at its root (the per-domain ones are now redundant but harmless) so Godot does not import game tables as translations — it was generating ~120 `.translation`/`.csv.import` sidecars nothing loads; `FileAccess` reads the CSVs regardless, and a future export preset must include `data/**` explicitly — plus the `world_state_index.png` / `world_province_index.png` / `world_biome_index.png` hit-test bitmaps are **generated** by `tools/import_azgaar.gd` from the Azgaar JSON export in `assets/maps/<id>/` — hand-edits are overwritten on re-import; lasting changes belong in Azgaar. **There is no map render PNG** (owner ruling 2026-09-11): the terrain is drawn by the game from the pack's cells — `geography/vertices.csv`, `cells.csv` (vertex ids, height, biome, water kind, neighbours) and `coasts.csv` (land and lake shores) — through `MapTerrain`, one vertex-coloured mesh whose colours come from `data/terrain_palette.csv` (a land tint per biome, sea, lake, and line colours) and whose relief and stroke widths come from `balance.csv` (`map_relief_*`, `map_light_*`, `map_river_*`, ...). The sheet is parchment (owner ruling 2026-09-12): `terrain_palette.csv` is one narrow warm-brown scale, the sea is the same sheet greyed a step, and `WorldMapView` lays a seamless `NoiseTexture2D` grain and a radial vignette over it in screen px (`map_paper_*`) — the map is printed ON the paper, so the paper does not zoom. **There are no coloured country areas**: `map_political_alpha` is 0, so `_draw_political_wash` returns early; ownership reads from a **bold dashed** kingdom border and **thin dashed** province seams, both stepped along the line's own arc length by `MapGeometry.dash_polyline` / `dash_segments` (Godot's `draw_dashed_line` restarts its phase per call, which turned the B-spline rings to mush). **Every dashed line is cut ONCE per zoom, never per frame** (2026-09-13, after `tools/bench_map.gd` found the per-frame cut and its one-command-per-dash drawing holding a pan at 4–9 fps): `MapDashCache` (`scripts/engine/`, pure, tested) keeps each line set — a kingdom's rings, a realm's seams, every lane — cut in NATIVE px for the current zoom as ONE polyline whose vertices carry a phase (dash / gap / an invisible jump between lines), thinned to `map_dash_min_step_px`; a frame transforms it with one `Transform2D * PackedVector2Array` and draws it with one `draw_polyline_colors`, the phases coloured ink / pale (the chequered border) or ink / clear (seams, lanes). A zoom or an ownership change empties the cache. What is left per frame is the strip builder's cost per vertex. Never go back to `draw_multiline` for a dashed layer: with a width above 1 px it is one canvas command per pair. The bench went from 4–9 fps to 28–87 fps on a pan. **The terrain decor is ONE mesh over ONE atlas** (2026-09-13, the decor rework the owner approved before filling the map with hamlets, fields and building icons): `MarkAtlas` (`scripts/engine/`, pure) shelf-packs the terrain art into one padded sheet with mipmaps at load, `MarkMesh` turns a list of marks `{pos, texture, height, color}` into one `ArrayMesh` of standing quads in NATIVE px (y-sorted, tint as vertex colour), and `WorldMapView._draw_terrain_decor` is a single `draw_mesh` whose `Transform2D` is the view's offset and zoom — rebuilt only when ownership changes (`decor_mesh()` keyed on `_ownership_sig`), never per frame or per zoom; the GPU clips what is off screen. That took the political pan from ~29 ms (decor 7.5 ms of `_draw` plus ~10 ms of the renderer's canvas-command CPU) to the heights view's ~10 ms. Every new layer of marks — hamlets per manor, field patterns per chief good, building icons — goes through the same two classes: never one `draw_texture_rect` per mark again. `terrain_sprites()` remains as a test seam only. `MapPalette` and the wash code stay in place — putting the colour back is one number in `balance.csv`, no code — and `MapPalette.color_of` still tints the country card, the map detail panel and the military bars. `WorldMapView` draws the coasts, rivers, routes, every kingdom's border, the province seams, the labels and a scale bar itself, so conquest redraws with no new art. Rivers are smoothed once per course (`MapGeometry.smooth_open`, cached — the pack stores raw polylines whose corners read as kinks), **in the pack's own order, which IS source → mouth** (Azgaar writes a river's cells that way and the importer keeps them; the earlier "the end nearer the coast is the mouth" guess turned short coastal rivers round, owner 2026-09-13), **clipped to the land at both ends with each cut bisected to the shoreline** (`_trim_to_land` / `_shore_between`: Azgaar runs a mouth one cell out to sea, and a river must begin where the sea ends, never in it), and drawn as a **solid tapered ribbon** (owner 2026-09-13) — `MapGeometry.ribbon` builds a triangle band whose half-width varies per point, because `draw_polyline` takes one width for the whole line. The river is **a point at its source and widest at its mouth**, swelling as `t^map_river_taper_gamma` (`WorldMapView.river_taper`; owner 2026-09-13, reversing the same morning's ruling); no caps — the mouth's flat cut lies on the shoreline. There is no soft halo band, and `map_river_alpha` is 1 — below 1 the ribbon's overlapping triangles on tight bends show as blots. **The sea is four flat bands by distance from the shore** (owner 2026-09-13, after the reference chart; the same day's hatching rings are GONE — owner: completely wrong): `SeaLayer`, a Node2D child of the view drawn `show_behind_parent`, paints ONE quad through `sea_bands.gdshader`, which samples the pack's `world_sea_distance.png` — every pixel its distance to land in native px, baked by `MapIndex.bake_sea_distance` in the importer (`tools/bake_sea_distance.gd` bakes it for a pack imported earlier; a test asserts it exists at the canvas size) — into `sea_near` / `sea_nearer` / `sea_far` / `sea_deep` at `map_sea_band_*_px`, each edge a `map_sea_band_soft_px` fade, over a fixed simplex wave grain (`map_sea_wave_*`, part of the drawing, so it zooms; its seed is data). **Sea cells are NOT in the terrain mesh** any more (lakes are), so the land mesh draws over the sea and the shore is the land's own edge; the view sets the layer's position and scale to its offset and zoom each frame. **A compass rose** (library M-13, drawn as vectors in the scale bar's ink) is fixed in the top-right corner, `map_compass_*`. **Ships and a whale are printed on the open sea**: `data/sea_art.csv` rows placed by `MapObjects.sea_decor` over the sea cells by AREA (one candidate per `map_sea_decor_spacing_px` square, hashed from the cell id — the pack's sea cells are few and huge, never more than two hops from land, so nothing is per cell), thinned by `map_sea_decor_density`, kept `min_shore_px` off the land coast and `map_sea_decor_min_gap_px` apart from each other — never overlapping (no seed, no state), tinted `sea_ink` at `map_sea_decor_alpha`, art from `assets/decor/` (library D-19 carrack, D-20 cog, D-22 whale — no monsters, owner 2026-09-12); a missing PNG simply draws nothing. The scale bar is bottom-right, over the vignette, and restates itself at every zoom: the pack's own `distance_scale` / `distance_unit` from `map_info.csv`, rounded down to the 1-2-5 ladder by `MapGeometry.nice_step` so it reads "200 km" and never "187 km". Settlement art draws at its tier's **share** of the largest drawing's height — the `size` column of `data/settlement_art.csv`, capital 1.0 down to hamlet 0.25 — never at the PNG's own pixel height, which made the hierarchy untunable without regenerating art. Only a **clicked** object is ringed; hovering names it in the tooltip and swaps the left column but draws nothing on the map (owner 2026-09-12). All pack coordinates are the JSON's own (2560×929 for `beria`); nothing is calibrated or scaled at import. The importer needs only the `*Full*.json`; it never reads a PNG.

## Stack

- **Godot 4.x + GDScript** (typed GDScript everywhere: type hints on vars, params, returns).
- **GUT** (Godot Unit Test) for tests. The simulation engine must be unit-testable headless.
- **OpenAI API via raw HTTP** (`HTTPRequest` node) — there is no GDScript SDK. Model IDs and prices live in one config table (see PRD §8), not scattered through code.
- **Run:** `/Applications/Godot.app/Contents/MacOS/Godot --path .`
- **Test:** `./run_tests.sh` (runs the full GUT suite headless; the suite must report the **expected error count** — any other count is fatal. That is "Errors 2" while the `gdai-mcp-plugin-godot` GExtension is installed, whose class-database probing GUT cannot resolve headless, and 0 without it; the script keys off `gdai_mcp_plugin.gdextension`, which is git-ignored along with `bin/`, so a fresh clone expects 0 until the binaries are copied in from the plugin zip). `run_tests.sh` exports `CC_FORCE_OFFLINE=1` so the suite can never make a live API call even with a real `.env` present.
- **`.env`** (git-ignored, dev-convenience source for `OpenAIClient.load_config()`; `.env.example` documents the keys — `OPENAI_API_KEY`, `LLM_MODEL`/per-tier overrides, `LLM_MAX_OUTPUT_TOKENS`) overlays defaults and is itself overlaid by `user://config.json` (player override); a missing key or `CC_FORCE_OFFLINE=1` fails closed to `offline_mode: true`.
- **`user://config.json`** (git-ignored, read by `OpenAIClient.load_config()`; missing/unreadable/malformed file, or an empty `api_key`, all fail closed to `offline_mode: true`):

## Architecture invariants (do not violate)

1. **The engine decides; the LLM only writes dialogue.** Concern scans, advisor suggestions, opinion drift, faction power, and escalation are all deterministic engine code. A minister's suggestion is a real `action_code` with real params — always legal, always affordable. Never let the model invent actions. The model may also propose **world deltas** (owner ruling 2026-09-09), but only on paths listed in `data/world_schema.csv`, each clamped to that path's `llm_cap`, each carrying a reason, and only on the player's own realm; the engine still picks the speaker and applies everything through `WorldLedger`.
2. **Determinism.** One seeded RNG stream owned by the engine. No `Time.get_*`, no wall-clock, no unseeded `randi()` inside simulation code. Identical save + identical inputs ⇒ identical state. LLM output enters the engine only as validated action codes, clamped enums (e.g. `tone` deltas capped at ±3), and schema-listed world deltas clamped to their caps.
3. **Simulation core is engine-pure.** Keep sim classes as `RefCounted` (no Node/scene dependencies) so GUT can run them headless. UI observes state via signals; it never mutates it directly.
4. **Readable causality.** Every opinion change carries a reason string at creation time (`−8: revoked noble tax exemption (opposes, centralism)`). Never write an opinion delta without one.
5. **Authored prose never names a kingdom.** The map is a generated Azgaar
   export, so story text, fact text, role names and templates say
   `{player_realm}` / `{raider_realm}` / `{neighbor_realm}` / `{empire_realm}`;
   `DataRepository.fill_realms()` substitutes the bound kingdom's label at
   load. Structural columns keep using the slot itself (`resolve_realm`).
   A re-export that renames the world should touch
   `data/maps/<id>/realm_bindings.csv` and nothing else — tests included:
   fixtures derive their kingdom, capital and roads from the pack, never
   from a literal name.
6. **Territory is state, not pack data.** The map pack ships the *starting*
   border; who holds a province now lives in `GameState.province_owner`
   (only what has moved) and moves through `MapOwnership.set_owner`, which
   requires a reason like every other state change. A kingdom's live outline
   is the merge of the loops of the provinces it holds
   (`province_borders.csv`), so conquest redraws the border, recentres the
   label and repaints the land with no new art. Hit-testing reads the
   province index bitmap — geometry, which never goes stale — and looks the
   owner up; never trust `world_state_index.png` for ownership.
7. **Save = one JSON file.** All state in memory, serialized whole. No database, no partial saves.
8. **Every order carries a cost.** `OrderCosts` guarantees an explicit (gold, grain, population) or hidden (opinion, relationship, attribute) cost per executed order from `data/order_costs.csv` (polarity per metric in `data/metric_polarity.csv`); `COUNCIL_CONSULT` and `EVENT_CHOICE` are the listed exemptions. A typed order is ONE model call returning `{narrative, impacts}`; the screens print the narrative and then the ledger lines that actually applied, so a narrative that overreaches is visible as such.
9. **Cost discipline.** Clicked suggestions bypass the LLM entirely. Low-stakes minister lines use trait-tinted templates with no API call. Reserve the flagship model for rare confrontation/betrayal scenes only.
10. **The columns divide by kind** (owner ruling 2026-09-10). The LEFT
    column is FACTS: the realm dashboard, the country under the cursor, the
    host while the military layer is on, and the fact card of whatever the
    player clicks on the map — clicking an object replaces the left column,
    never the right. The RIGHT slot is PEOPLE AND TALK: the council column,
    the dialogue panel, and the speaker's dossier, which stands at the top
    of it over their words — a thumbnail, name, seat and standing, with
    BIO / SKILLS / TIES pages that open in the talk's space and hand it
    straight back, because the column cannot hold both. So a map click
    never displaces the council, and the map only narrows for the council.
    The left column's width is fixed
    (`ScreenLayout.LEFT_WIDTH`, 120 design px): anything put in it must wrap
    — a label that cannot wrap sets a minimum width and pushes the column
    over the map — and scroll rather than grow. Each screen owns one
    `_refresh_left()` that applies the precedence (card > hovered country >
    military > the column's own content); no panel hides its own siblings.

UI screens are self-contained scenes signaling up to GameRoot; state mutations only via Game.

**The interface's dimension icons are game art** (owner 2026-09-13, after `development/exmaples/UI.png`): the resource strip and the realm card show library `I-40` and `I-47`..`I-61` — one coloured still-life per dimension (treasury, people, host, drill, unrest, legitimacy, contentment, church, the five arms, towns, country), the v2 pencil core on `[C-ICON]`, cut out by `post.py --tier icon`, then trimmed to its alpha box and fitted into 64 px (drawn at 24 design px × the ~3× largest window scale — an installed file is sized by its USE, never one size for all, owner 2026-09-13) and installed by `install_map_art.py ui` (`assets/flux/ui_icon_art.csv`) into `assets/icons/<key>.png`, which `data/resource_icons.csv`'s `texture` column names. They KEEP their colour. `ResourceIcon` draws the art when the key has some and the gold glyph otherwise; `BarChart` / `PieChart` rows with a `dimension` key draw that art in place of the label, and the label is the row's floating tooltip (`_get_tooltip`). Words stay only where the row is a name (provinces, goods).

**Portrait art comes from the library's `K-` chapter, not `C-`.** `C-01`..`C-55` are generic archetypes; the game's cast is the 21 named people in `data/founding_council.csv` and `data/roles.csv`, and library §2.6 has one `K-` entry per character id with a `**外貌**` line (looks and clothing only — without it `generate.py` falls back to the portrait prompt and its props). Ages and traits in those entries are taken from the two CSVs, not invented. `assets/flux/cast_art.csv` maps character id to `K-` number for `install_map_art.py cast`, which fills `assets/portraits/<id>.png` (96 px chip, from `[C-BUST]`) and `assets/portraits/full/<id>.png` (660 px figure, from `[C-FULL]`). Portraits keep their colour — they are looked at, not tinted.

**Thematic map layers.** The map has three mutually-exclusive themes, each on its own bottom-bar toggle and each replacing the political wash rather than sitting on it — one map, one theme, and the symbols drop their realm tint while a theme is up. PROVINCES draws the internal seams; **HEIGHTS** ramps the land through the `heat_N` stops of `terrain_palette.csv` (`MapTerrain.heat_mesh`, one prebuilt mesh, one draw call); **ECONOMY** (owner 2026-09-13, after `development/exmaples/economyView.png`) draws the land as its **manors** — the pack's Voronoi cells, one estate each — in one flat mesh (`WorldMapView.manor_mesh`, rebuilt only when a province changes hands) coloured by the cell's live holder and deepened by its biome's habitability (`MapEconomy.land_value`), with the cell edges ruled in. A **working manor** is a cell a producing settlement stands in (`MapEconomy.burg_cells` finds the cell by point-in-polygon at runtime — the pack gives burgs no cell id, and re-importing would overwrite hand-edited pack tables); it is filled dark and carries a badge with the icon of its chief good (`goods_art.csv`, falling back to the category glyph `tag_*` in `resource_icons.csv`), ringed in that good's CATEGORY colour (`data/goods_palette.csv`) over a chip with its units. Badges follow the town LOD rule, never overlap (a smaller producer's badge is dropped, its dark fill kept), and stand in for the settlement drawings while the layer is up. Every colour and size is `political_palette.csv` `manor_*` / `balance.csv` `map_manor_*`. **MILITARY** (owner 2026-09-13, after `MilitaryView.png`) draws each of the player's regiments as a counter: a dark square with a glyph — swords, a crown for `MapObjects.royal_regiment` (the land regiment nearest the capital), waves for a fleet — joined to a box in the realm's hue stating the headcount. A counter is a share of the largest settlement drawing's height (capped at `map_army_badge_max_px`), so it always reads smaller than the towns, and it never covers one: every settlement drawing and pin is an obstacle, and a counter that would overlap a town or another counter is pushed down to sit under it (`army_*` / `map_army_*`). `MapEconomy` sums `economy/production.csv` (recorded per burg) into provinces, and provinces into realms **through live ownership**, so a conquest moves output from one realm's column to another's with nothing to recompute. The ECONOMY layer also puts `EconomyPanel` in the LEFT column, exactly the way the military layer puts the host there, reading off the same palette so the column and the map are one legend.

**Map symbol art is GREYSCALE on purpose.** Everything in `assets/terrain/` and `assets/settlements/` is drawn through a multiply tint of the realm that holds its province (`WorldMapView.realm_tint`), so the art carries only VALUE and the hue comes from `political_palette.csv`. Sepia art times a realm colour stays sepia — the brown wins and the parchment shows through the coloured washes; grey times a realm colour IS that colour. Every mark — terrain and settlement alike — is also lightened 45% toward the paper IN THE FILE rather than drawn translucent: a translucent mark cannot occlude the one under it, and a wood is a clump of overlapping marks. One fade value across the whole sheet, so nothing sits at a different depth from its neighbours. Province is fixed geometry (resolved once from the province index bitmap); OWNER is looked up live, which is what makes conquest recolour a realm's towns and woods with no new art.

**The game must look right at ANY window size, not just integer multiples of the design viewport.** `rendering/textures/canvas_textures/default_texture_filter` is **Linear with mipmaps** and every art `.import` generates mipmaps (the three `*_index.png` hit-test bitmaps are the exception — they are data read as `Image`, never sampled). Nearest is only crisp at an exact integer scale; on a 1512x982 or 2560x1600 display — most real monitors — it point-samples every texture and the screen reads as ragged. Mipmaps matter as much on the way down: a 256 px terrain symbol is drawn at ~20 design px. Fonts need nothing: Godot re-rasterises them at the window resolution under `canvas_items` stretch, so they are sharp at every ratio. **`tools/snapshot_screen.gd --resolution WxH` renders through the REAL window** and is the only faithful way to check this; its `--scale` mode uses a SubViewport and a scaled Control, which looks similar and exercises a different path.

**The design viewport is 1280x720** (raised from 640x360 on 2026-09-12). `project.godot` stretches with `canvas_items`, so the game lays out in design units and draws at the window resolution; at the default 1280x720 window that is now 1 real pixel per design pixel, which is the whole point — a raster drawn into an N-design-px box gets N real pixels to work with instead of N/2. Every design-px number was doubled with it: `balance.csv`'s screen-px keys and the thresholds compared against `view_scale()` (which doubles for the same framing), the `const`s in `scripts/ui`, every font size, and the literals in the drawing code. Three kinds of number were deliberately LEFT ALONE, and the same test applies to anything added later: values already multiplied by `view_scale()` (`map_sprite_scale`, `map_label_scale_px`, `map_river_discharge_scale`), values in some texture's OWN pixels (`MAP_EDGE_CROP`, `PANEL_ART_SOURCE_INSET`, `ResourceIcon`'s `u := s / 9.0` glyph grid), and values in native map px (`PREVIEW_SPAN`). `tests/ui/test_display_fit.gd` pins the viewport.

**The UI and the map are a BRIGHT, MODERN theme** (owner 2026-09-13, replacing the parchment look of 2026-09-12, which read old and dim): `UiPalette` holds dark slate ink on near-white rounded cards with a soft shadow, a royal-blue accent (the constant is still called `GOLD`) and gold trim; each line keeps its parchment predecessor in a comment. `ui_panel_art` is 0, so the vellum plate below is off; the map's land, sea and realm washes were brightened in `terrain_palette.csv` / `political_palette.csv`, and the paper grain is a trace with no vignette. **Fonts divide by job** (owner 2026-09-13, all OFL, licenses in `assets/fonts/`): **UnifrakturMaguntia** for the game title, headers (`UiPalette.style_header`, drawn `TITLE_SIZE_SCALE` larger because blackletter reads small; ALL-CAPS header text is set in title case by `readable_title`, since blackletter capitals in a row cannot be read) and the **kingdom names on the map** (`map_label_font`, drawn in the name's own case with `map_label_tracking` near 0); **Cinzel Decorative** on tab buttons (`style_tab`); **Cinzel** for everything else — dialogue, options, long text — as the theme default and the transcript's RichTextLabel fonts (the file is one weight and has no italic, so bold is an emboldened and italic a slanted `FontVariation`), plus the scale bar and the heraldic shield (`display_font`). The transcript's ink is set on RichTextLabel's own `default_color` — it does not inherit the Label colour, and unset it drew white. The (previous) parchment note follows for reference: `UiPalette` held dark ink on cream — every colour picked to read on Cream Laid `#EDE3CE`. Panels draw as `assets/ui/panel_vellum.png` nine-sliced (`UiPalette.panel_style` returns a `StyleBoxTexture` when `balance.csv`'s `ui_panel_art` is on and the art loads, else the old flat style — no screen knows which). `StyleBoxTexture` has no scale of its own, so the source PNG **is** the drawn size: the plate is cut to 128 px for a 20-design-px corner. Chart colours live in `data/chart_palette.csv` and were darkened for the light ground with their hue spacing unchanged. **`tools/snapshot_screen.gd` renders one screen to a PNG** (`--screen court|conversation|day_run|main_menu`) the way `tools/snapshot_map.gd` renders the map — it applies `UiPalette.build_theme()` itself, because GameRoot normally does and a themeless shot would show Godot's default grey buttons and lie about the UI.

## Conventions

- GDScript style: `snake_case` files/functions/vars, `PascalCase` classes, signals named in past tense (`opinion_changed`).
- The API key is read from a local git-ignored config file — never committed, never shipped in a build.
- Every engine formula (opinion drift, faction power, cohesion) gets a GUT test with hand-computed expected values before UI work uses it.
- Build order is PRD §6, strictly: briefings/suggestions → opinion drift → debates → recruitment → factions to stage 3 → chapter framework → faction stages 4–6 (Tomas's faction only, data-capped) → raid defense → chapter-1 event chains → art integration. The MVP is a complete Chapter 1 (PRD v2.0, §7); succession/assassination/aging and stages 4–6 for other factions remain post-MVP.
