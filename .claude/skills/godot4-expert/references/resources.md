# Resources: Godot's Data Layer

A `Resource` is serializable data with an optional script. Textures, scenes, audio, animations, themes, physics materials — everything in the FileSystem dock except folders and scripts' raw text is a Resource. Mastering *custom* resources is what separates data-driven Godot projects from hardcoded ones.

## 1. Built-in resource types you must know

| Category | Resources |
|---|---|
| Scenes | `PackedScene` |
| Visual | `Texture2D` (`CompressedTexture2D`, `AtlasTexture`, `ViewportTexture`, `GradientTexture2D`), `SpriteFrames`, `Mesh` (`ArrayMesh`, primitives), `Material` (`StandardMaterial3D`, `ShaderMaterial`, `CanvasItemMaterial`), `Shader`, `Environment`, `Sky` |
| Physics | `Shape2D`/`Shape3D` (Rectangle, Circle, Capsule, ConvexPolygon, ...), `PhysicsMaterial` (friction/bounce) |
| Animation | `Animation`, `AnimationLibrary`, `Curve`, `Curve2D/3D`, `Gradient` |
| UI | `Theme`, `StyleBox` (`StyleBoxFlat`, `StyleBoxTexture`), `Font` (`FontFile`, `FontVariation`), `LabelSettings` |
| Audio | `AudioStream` (`AudioStreamOggVorbis`, `AudioStreamWAV`, `AudioStreamRandomizer`, interactive/playlist streams) |
| Tiles/Nav | `TileSet`, `NavigationMesh`, `NavigationPolygon` |
| Misc | `Script`, `InputEvent` (yes, events are resources), `JSON`, `ConfigFile`-adjacent (`ConfigFile` is RefCounted, not Resource) |

`Curve` and `Gradient` are underused gems: `@export var damage_falloff: Curve` gives designers a drawable curve in the Inspector; sample with `curve.sample(t)`.

## 2. Custom resources — the pattern

```gdscript
# res://resources/enemy_stats.gd
class_name EnemyStats
extends Resource

@export var display_name: String = "Enemy"
@export var max_health: int = 10
@export var move_speed: float = 60.0
@export var damage: int = 1
@export var xp_value: int = 5
@export var death_sfx: AudioStream          # resources nest freely
@export var drop_table: Array[ItemDrop]     # typed arrays of other custom resources
```

Now `slime_stats.tres` and `bat_stats.tres` are data files creatable in the Inspector (right-click FileSystem → New Resource → EnemyStats), and the enemy scene consumes them:

```gdscript
class_name Enemy
extends CharacterBody2D

@export var stats: EnemyStats

@onready var health: int = stats.max_health
```

Why this beats exporting loose vars on the enemy: stats are shared (one balancing edit fixes every slime), diffable in git, hot-swappable (`@export` a different .tres for an elite variant), and composable (an `ItemDefinition` can hold an `EnemyStats` for a summon item).

More power:
- Resources can have methods and signals. `emit_changed()` / the `changed` signal notifies listeners when data mutates — Nodes can `stats.changed.connect(_refresh)`.
- `@export_group("Combat")`, `@export_range(0, 100, 1)`, `@export_enum("Melee", "Ranged")`, `@export_multiline`, `@export_file("*.tscn")` polish the Inspector.
- `@tool` + `_validate_property()` / `_get_property_list()` for dynamic inspectors (advanced).
- A resource script can `extends` another custom resource (`class_name BossStats extends EnemyStats`).

## 3. Loading, caching, duplication semantics

**Resources are cached and shared.** `load("res://x.tres")` twice returns the *same object*. Two enemies exporting the same `.tres` share one instance — mutating `stats.max_health` at runtime changes it for **everyone** (and in the editor, can write back to the .tres!).

- Treat `.tres` data as **read-only templates**. Copy mutable values into the node (`health = stats.max_health`) or duplicate: `var my_stats := stats.duplicate(true) as EnemyStats` (`true` = deep — also duplicates nested resources; note: `duplicate()` and Arrays/Dictionaries inside resources have subtle sharing rules, deep-duplicate when in doubt).
- `@export var local_to_scene := true`... actually on Resource it's `resource_local_to_scene` — set it on a resource that must be unique per scene instance (e.g., each enemy's own ShaderMaterial so flash effects don't sync).
- `preload("res://...")` — parse-time, path must be constant, great for scenes/stats known upfront. `load()` — runtime, dynamic paths.
- Background loading for big scenes: `ResourceLoader.load_threaded_request(path)` then poll `load_threaded_get_status()` and fetch with `load_threaded_get()` — this is how you build a loading screen.
- `ResourceSaver.save(resource, "user://...")` writes a resource to disk. `res://` is **read-only in exported games**; all runtime writes go to `user://` (a per-OS app-data dir; see ProjectSettings for the path).
- `ResourceUID` / `uid://` paths survive file moves; prefer uid references in code only when generated by the editor.

## 4. Resources for save games — and the security caveat

Custom resources make seductive save files (`ResourceSaver.save(save_data, "user://save.tres")`), but **loading a resource can execute code** (embedded scripts). Loading a save file a user downloaded from the internet = arbitrary code execution. Policy:

- Single-player, saves never shared: resource saves are acceptable and convenient. Load with `ResourceLoader.load(path, "", ResourceLoader.CACHE_MODE_IGNORE)`.
- Anything where files may be shared/modded/synced: serialize to **JSON** (via `JSON.stringify`/`parse`) or `ConfigFile`, or binary `FileAccess.store_var(data, false)` with `full_objects=false`. Store plain Dictionaries/Arrays; rebuild typed objects on load.
- Either way: include a `version` field and write migration code from day one.

See systems-cookbook.md for a full save system implementation.

## 5. Resource vs Node vs Dictionary decision table

| Need | Use |
|---|---|
| Data edited in Inspector, saved as files, shared across scenes | **Resource** |
| Behavior in the world, per-frame ticking, tree position | **Node** |
| Throwaway structured data, JSON interchange, save-file payloads | **Dictionary / Array** |
| Runtime-only logic object (no serialization, no tree) | **RefCounted** class |
| Item *definitions* | Resource (`.tres` per item) |
| Item *instance in inventory* (count, durability) | Small RefCounted/Dictionary pointing at its definition Resource |
| Enemy archetype stats | Resource |
| A specific enemy's current HP | Node's own variable |
| Dialogue tree content | Resource (or JSON if written by external tools) |

Memory model: Resource/RefCounted are reference-counted (auto-freed at zero refs; beware reference cycles — use `weakref()` to break them). Nodes are manually managed (`queue_free()`).

## 6. .tres text format

```
[gd_resource type="Resource" script_class="EnemyStats" load_steps=2 format=3]

[ext_resource type="Script" path="res://resources/enemy_stats.gd" id="1_stats"]

[resource]
script = ExtResource("1_stats")
display_name = "Slime"
max_health = 12
move_speed = 45.0
damage = 1
xp_value = 5
```

Same conventions as .tscn (see nodes-and-scenes.md §5): only non-defaults written, ext/sub resources declared first, omit `uid` when authoring by hand. `.tres`/`.tscn` are text; `.res`/`.scn` are the binary equivalents (smaller/faster; text is better for git).
