# P4 WAR ROOM task-window evidence

This evidence-only step captures existing task controls; it changes no game code, scene, resource, data table or art. It does not accept whole P4, combat behaviour, natural battle frequency or owner playtesting.

Baseline: `75e10a30093a1a56245c42050528f62b7dd6ca91`. Real Godot 4.7.2 `ed1daf0bf`, Metal Forward+, Apple M5 Pro. Window comparisons use 1920×1200 and the 1280×720 design minimum. The standard is the existing daylight WAR ROOM and its parchment folio, following taste's “Name every reading”, “Read in a book face; shout only in titles”, “Commands look like commands”, “A warning speaks in the page’s own rubric”, and “Sharp up close, clean from far, at any window size”. These are state/size comparisons, without a new look variant.

## Reproduce and scope

Artifacts live in [evidence/P4-war-room-task-windows](evidence/P4-war-room-task-windows). From the frozen checkout, run `python3 docs/reviews/battle-system/evidence/P4-war-room-task-windows/reproduce.py.txt`, then `python3 docs/reviews/battle-system/evidence/P4-war-room-task-windows/capture_all.py.txt`. The capture script resumes by skipping names already present in `capture-results.json`; to reshoot all cases, first move that JSON aside (the script overwrites the corresponding PNG/logs). Import once first through `/Users/samuelzhang/game_design-wt/godot_lock.sh /Applications/Godot.app/Contents/MacOS/Godot --headless --path . --import`. Capture commands never use headless rendering. `capture-results.json` retains exact successful invocations; `frozen-inputs.json` records input hashes and source trees. The ignored fixture is a copy of the existing snapshot tool with sequential resource prewarming and one per-frame staging callback, not a replacement production tool.

The existing `--quiet --battle-case field` fixture creates actual contact by placing a hostile unit 1000 metres from the first sorted own land unit, advances the day and acknowledges its saved encounter through Game. At frame 26 the added fixture derives that same own unit and its actual sheet from current pack/state, then the tool clicks WAR ROOM, lays that sheet, leans to 1.5 metres and clicks the unit. No pack or realm name is embedded in the fixture. Before constructing GameRoot, the temporary tool loads and retains `BootLoads.TABLES + GameRoot.OVERLAY_SCENES` sequentially. This uses the same resources but avoids the repeated startup stall observed with parallel overlay loading; it does not establish normal-launch acceptance. All retained final captures use this same prewarm setup. The default campaign formation, labels, targets, prices and legality all come from existing presentation and engine code.

Remote cases keep the king at his real initial campaign position and assert that the unit is outside his command range; the local case places him at the unit. “Poor” sets the treasury to zero; “law” stages an agreed protective ceasefire and chooses Flank attack through the existing OptionButton selection signal. These are controlled setup changes, not naturally reached campaign or negotiation evidence. Menu shots use real viewport clicks to open the task, target and deployment lists. Pending/delivered/local cases click the actual Send task button, reaching the existing Game transaction. Delivered stages the resulting courier at its actual aim with an empty remaining path, invokes existing `CourierSystem.ride_day` (including receipt and finished-courier removal), and emits the state refresh, rather than simulating its journey. This proves receipt presentation after the actual arrival lifecycle, not elapsed travel, battle execution, save/load or determinism. All text is rendered by the existing folio; the fixture never writes a label.

## Observations and remaining gaps

Implementation observations (not independent acceptance): the known selected unit's name, facts, default task, target and deployment choices fit both baseline sizes. Remote pricing names filing and courier gold and states when the order takes effect. Treasury-zero and agreed-ceasefire refusals remain readable and disable Send task. Pending and received lines fit both sizes, with Cancel task visible. The remote pending quote correctly drops the new courier fee when sharing the waiting courier; after arrival cleanup it quotes a new courier again. The local command costs only the filing gold and immediately becomes Received without a courier. These observations cover the default Frontal charge with Any enemy and Keep deployment, not the execution of every offered task/target/formation combination.

Concrete existing gaps for the dispatcher, with no fixes in this evidence PR:

- All three OptionButton popups render as flat grey default Godot menus with radio dots and much larger type than the parchment. Reproduce by running `P4_CASE=tasks`, `targets` or `formations` with the retained capture command; see the three raw PNGs and `options-comparison.png`. This breaks the shared material/medium principle.
- Treasury-zero text exposes the internal action id: “Cannot afford BATTLE_TASK (needs 1 gold)”. Reproduce `P4_CASE=poor`; see both poor-condition PNGs. It is legible but violates the game's own voice and exposes implementation vocabulary.

The independent Review rubric below was formed after inspecting all raw images and crops, before reading the implementation observations. A readable captured state is bounded evidence, not approval of the surrounding map, miniature, animation or all possible task combinations.

## Independent visual Review

Review: `01a15a48-3abe-7d82-944e-6629a84626d6`, sole Review and independent critic. Inspected all 13 native PNGs and all six sheets before reading implementation observations. Standard: this daylight WAR ROOM/folio and the repository taste principles above. These are comparisons of existing states and sizes, not proposed design alternatives.

Size ranking: 1920×1200 first for reading margin and separation; 1280×720 second, with smaller but readable captured facts, status, price and actions and no visible clipping. Condition ranking: closed baseline/pending/received/local and refusal states retain the folio's visual language; the three open menus rank last because their oversized grey panels break it. No ranking implies that a refusal or pending state is preferable gameplay.

- Hierarchy: the large unit folio and upper sheet/legend compete before the tiny pieces; within the folio, identity precedes facts, then task/status and commands. The task subsection is discoverable, though subdued selectors and idle Send task do not strongly advertise interaction.
- Value: dark ink on light paper separates facts, status and refusals clearly; pale grey selector text/arrows and idle controls are weaker, especially at minimum size. Disabled Send task is visibly quieter. Warning text keeps the facts' dark ink and readable size.
- Colour: parchment, brown leather/wood and muted red rubric belong together; the popup's neutral grey and bright white type leave that warm family.
- Medium: the folio belongs to the existing table; flat default popup fills and radio dots read as an external software menu rather than crafted paper/leather. This remains an existing defect, not visual approval.
- Edges: the popup has an abrupt rectangular edge; the folio also has multiple nested decorative borders, which add frame-within-frame noise against “Material over ornament”. No clipped task/status/action edges appear in the captured closed states.
- Scale: closed task controls fit both captured sizes; popup type is much larger than adjacent facts and its panel spills beyond the folio. Open menus at 1280×720 and long combined current-plus-pending status remain untested.
- Sharpness: native 1920 text is crisp; minimum-size text is smaller and visibly raster-stepped in the ×3 crops but readable. Enlarged sheets are comparison aids, not proof of native sharpness. No missing-glyph or overlap defect is visible in these task strings.
- Noise: repeated ornamental frames and popup radio dots add visual weight; no extra task icon obscures the words. The internal `BATTLE_TASK` refusal token breaks the game's own voice and needs a separate copy fix.

Evidence acceptance: accepted as a faithful, bounded record of the captured existing controls and staged state transitions, with the defects above preserved for the dispatcher. The UI itself does not receive a clean visual pass. No game/UI/resource/art repair belongs to this PR; no whole-P4, normal-launch or owner-playtest acceptance is granted.
